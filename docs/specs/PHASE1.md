## 三、视觉设计目标（最高优先级）

本项目面向拥有上千款 Steam 游戏的玩家，是个人收藏管理平台，不是企业后台。我非常重视界面美观，目标是成熟独立软件或高品质商业桌面应用的水准。

设计关键词：Premium Desktop Application、Cinematic Game Library、Dark Editorial Interface、Refined Typography、Elegant Motion、Immersive Cover Art、Modern Minimalism。

设计融合：

- Steam 游戏库的内容展示能力
- Apple Music 的精致排版和视觉层次
- Linear 的现代组件细节
- 高端数据仪表盘的信息组织方式

仅作为参考，不要照搬界面。

### 要做到

- 游戏封面是视觉主角：足够大、比例统一、不拉伸。
- 页面有明确的视觉重点和节奏，不同区域有不同的视觉权重（非对称布局）。
- 克制的配色，主要靠封面与背景图提供色彩，强调色只用于关键位置。
- 统一的字体、字号层级、间距系统。
- 细节到位：边框、阴影、遮罩渐变、悬停与焦点状态。

### 要避免

- 页面全是尺寸相同的矩形卡片
- 没有视觉重点的 KPI 堆砌
- 过度使用紫色渐变
- 到处发光的霓虹边框
- 大量没有意义的动画
- 不统一的字体和间距
- 游戏封面过小
- 缺乏内容层级
- 使用 Emoji 代替图标（所有图标统一使用 Lucide）

以 `docs/DESIGN.md` 为设计依据。需要完善设计细节时同步更新该文件。不得未经理由替换设计令牌、字体或组件系统。

## 五、Demo 模式与数据约定

本阶段不接入真实 Steam 数据，必须实现独立的 Demo 模式：

1. 使用单独的配置开关启用，默认开启。
2. 界面中明确、持续显示 DEMO 标识。
3. 演示数据与未来真实用户数据完全隔离。
4. 使用固定随机种子，保证相同条件下结果可复现（截图与测试结果一致）。
5. 数据覆盖：不同名称长度（含超长标题与中日英混排）、类型、游玩状态、封面情况。
6. 不得将演示统计伪装成用户真实记录。
7. 预留未来真实数据替换接口。
8. 通过 URL 参数或开关切换数据规模：默认 1500 款，另提供 5000 款测试场景。

### 封面图片素材

- 制作 **20–30 张高质量、具有不同视觉风格的本地演示封面**，优先用于主要展示区域和视觉验收，使游戏库具有足够丰富的视觉内容，而非全部采用相似的几何渐变。
- 其余游戏使用可复现的程序化封面（渐变、几何或程序化图案，配合标题排版）。这些正常的程序化封面与“缺失封面”状态必须明确区分。
- 默认素材全部本地可用，不依赖外部图片服务或图床，不使用真实游戏截图；所有 Demo 素材与真实用户数据分离。
- 可选：允许配置开关尝试加载公开封面，但必须处理失败回退，且默认关闭。
- **刻意让一部分游戏（建议约 8–10%）没有封面，另有一部分没有背景图**，用于测试占位组件。
- 占位组件本身也要精致，不能是灰块或破图图标。

### 私人游戏（预留）

- 数据模型中预留私人标记字段。
- 私人游戏默认不参与普通页面的展示、搜索、统计、推荐和截图。
- 在数据选择层实现隐私过滤，并编写基本测试验证。
- 本阶段不实现完整 Private Library 页面。

## 九、响应式与多分辨率适配（1080P / 2K / 4K）

目标：**1080P 要精致，4K 要充分利用空间，高 DPI 下要清晰，窗口缩放后要稳定。** 以 Windows 11 桌面为主要目标。

### 9.1 核心原则

1. 使用响应式布局，不得把页面宽度、卡片数量、字号硬编码为仅适用于某一分辨率。
2. **布局以 CSS 视口宽度为准，不以物理分辨率为准。** 不得假定 4K 显示器一定有 3840 CSS 像素宽度（Windows 缩放 150% 时 CSS 视口为 2560×1440，200% 时为 1920×1080）。
3. 优先使用容器查询（container queries）与 CSS Grid 自适应列数，因为侧边栏折叠会改变内容区宽度；仅在必要时使用 media query。
4. 4K 大视口下优先增加有价值的信息和可见游戏数量，而不是单纯放大所有组件。
5. 1080P 下保持合理信息密度，无拥挤、重叠、意外横向滚动。
6. 各档位的视觉品质、交互体验和设计语言保持一致。

### 9.2 布局规则（需写入 `docs/DESIGN.md`）

- **网格卡片宽度设最小值与最大值**（建议区间约 160–240 CSS px，具体由设计决定并记录），列数由容器宽度自动计算；封面比例不变。
- 内容区超过约 2400 CSS px 后：Library 继续增加列数但卡片不超过最大宽度；Dashboard 改为更多列的多栏布局而非拉伸；Game Detail 正文限制可读行宽，背景图与头部区域可铺满。
- 避免内容只占 4K 屏幕中央一小块，也避免卡片小到无法辨认。
- 侧边栏、顶部导航、Dashboard、游戏网格、详情页均自适应；窄窗口下侧边栏自动折叠，网格列数下降。
- 支持窗口化、最大化和动态调整窗口尺寸。

### 9.3 高 DPI 清晰度

- 图标使用 SVG，占位图使用 SVG/CSS 生成，天然清晰。
- 位图封面按 DPR 选择合适尺寸（`srcset` / `sizes`），避免高 DPI 下模糊。
- 细线边框、图表线宽与文字在 DPR 1 / 1.5 / 2 下都清晰（Recharts 需要专门验证）。

### 9.4 验收矩阵（CSS 视口 + deviceScaleFactor）

| 档位 | CSS 视口 | DPR | 说明 |
|---|---|---|---|
| 1080P | 1920×1080 | 1 | 基准 |
| 2K | 2560×1440 | 1 | |
| 4K 大视口 | 3840×2160 | 1 | 最大布局宽度压力测试 |
| 4K @150% | 2560×1440 | 1.5 | 4K 用户最常见的真实设置 |
| 4K @200% | 1920×1080 | 2 | 布局同 1080P，图片需更清晰 |
| 窄窗口 | 1280×720 | 1 | 侧边栏自动折叠，列数下降 |
| 小笔记本 | 1440×900 | 1 | 兼容检查 |

Playwright 中必须通过正确设置 `viewport` 与 `deviceScaleFactor` 来模拟，**不要只改变截图输出尺寸**。

**限制说明：** Playwright 只能用“CSS 视口 + DPR”近似 Windows 缩放，无法真正模拟系统级缩放。报告中必须如实说明，不得声称“已验证 Windows 125%/150%/200% 系统缩放”。

### 9.5 自动化检查（每个档位 × 每个已授权并实现的页面）

- 无横向滚动：`document.documentElement.scrollWidth <= clientWidth`
- 网格列数处于预期范围，并随容器宽度合理变化
- 卡片长宽比保持不变，封面无拉伸
- 无元素超出视口或相互重叠
- 侧边栏折叠/展开后列数重算正确，滚动位置不跳变
- 长标题截断为两行，卡片高度一致

### 9.6 测试分层

- **快速冒烟**（每次改动可跑）：1920×1080、1280×720 下已授权且已实现页面的核心检查；检查点 1 只检查 AppShell 与 Library，后续页面获准并实现后再纳入。
- **完整视觉回归**（检查点 4 运行）：完整矩阵、全部页面状态、截图保存。
