# Phase 2 · 检查点 5 报告：安全解压与“一键下载并解压”

日期：2026-10-31 · 分支 `phase-2/checkpoint-5`（基于 `phase-2/checkpoint-4`）。按用户 prompt，代码只做本地提交，不推送、不建 PR。提交号见交付回复。

## 1. 结论
**实现完成，待人工真实解压/完整链路验证。** 解压的安全规则已用真实文件和真实 7-Zip 验证，但**没有处理过任何真实作品**。

**重要依赖**：C5 的 prompt 要求 C4 先通过真实验证，但用户决定（2026-10-31）不等待，直接开始。C4 的真实下载至今未执行，所以整条链路最大的未知仍是 C4 §2 的下载入口。

## 2. 继承 C4 的约定
- 解压的输入只有“已完成的下载任务”。解压前重新核对每个文件的大小和 SHA-256，并确认它仍在原位置。
- 复用任务状态写法：每次写入带尝试号，旧尝试写不进去。
- 下载完成的含义没有改。解压是独立的任务，不改写下载状态。

## 3. 解压工具
| 格式 | 实现 | 版本与许可 |
| --- | --- | --- |
| ZIP（存储、Deflate、BZIP2、LZMA） | Python 标准库 `zipfile` | 随 Python 3.14 |
| RAR、RAR5、7z、自解压文件 | 用户安装的 7-Zip | 要求 ≥ 25.01；LGPL，含 unRAR 限制 |

- **7-Zip 不随项目分发**，也不提交到 Git。没有安装时，这些格式明确提示“需要 7-Zip”，ZIP 不受影响。
- **只从这些位置查找**：注册表 `SOFTWARE\7-Zip`，然后默认安装目录。不查 PATH，不受文件名影响。
- **最低版本 25.01**：更早的版本有链接越界漏洞（CVE-2025-11001、CVE-2025-11002 在 25.00 修复，CVE-2025-55188 在 25.01 修复，[来源](https://www.helpnetsecurity.com/2025/11/19/7-zip-vulnerability-is-being-actively-exploited-nhs-england-warns-cve-2025-11001/)，2026-10-31 查阅）。更旧的版本按“未安装”处理。
- 本机测试用 7-Zip 25.01。当前最新是 26.04，其修复内容未核实，建议用户升级。
- 调用方式：参数列表，不经过 shell，`--` 结束选项，隐藏窗口，只结束自己启动的进程。

## 4. 支持矩阵
| 项目 | 状态 | 依据 |
| --- | --- | --- |

| 嵌套压缩包 | 不递归解压 | 设计如此 |

## 5. 路径与资源边界
- **拒绝整包**：`..`、绝对路径、盘符、UNC、`:`（备用数据流）、Windows 保留名、结尾的点或空格、控制字符。规则按 Windows 的语义判断。
- **重复名**：按 NFC + 大小写折叠比较，相同就拒绝，不靠“后写覆盖前写”。文件和目录同名也拒绝。
- **特殊条目**：链接、硬链接、备用数据流拒绝。
- **已知缺口**：7-Zip 在 RAR 4 列表里不报告 Unix 链接，所以列表阶段认不出。实测写出的是普通文件，不是链接；最终检查也会拒绝任何重解析点。RAR 5 链接没有样本。
- **上限**：总量 500 GiB、单文件 200 GiB、50 万个文件、12 小时。看大小，不看压缩比，因为合法内容可能压缩比很高。
- **声明可能是假的**：ZIP 按实际读出的字节计数；7-Zip 运行时每 0.2 秒测量输出目录，超限就停。测试包含谎报大小的样本。
- **最终检查**：工具成功还不够。输出必须和列表完全一致（路径、数量、已知大小），且没有任何链接，否则不采用。

## 6. 暂存、冲突与提交
- 每次尝试写到 `<解压文件夹>/.atlas-extract-<任务号>`，和结果在同一个卷，所以提交是原子改名。
- 结果在 `<解压文件夹>/<作品编号>`。**已有目录不合并、不覆盖**，新结果改名为 `编号 (2)`。
- 下载的原文件始终保留。
- 清理只删除由任务号拼出的那个目录。删除失败时明确提示用户手动处理，不说已清空。

| 崩溃窗口 | 恢复 |
| --- | --- |
| 解压中 | 删除暂存，标记中断，可以重新解压 |
| 暂存完成未提交 | 同上 |
| 改名后未记完成 | 名称是任务自己选的，且文件数和字节数都一致才认领为完成 |
| 同名目录内容不符 | 不认领，标记中断，不动那个目录 |
| 记完成后结果被移走 | 显示“解压结果已经不在原位置”，可以重新解压 |

## 7. 一键流程
- “下载并解压”和“仅下载”是两种意图。只有前者会给下载任务打上流程标记，全部文件完成后才自动解压。
- “仅下载”永远不会自动解压，之后可以点“解压”。
- 对已下载的作品点一键，不会重新下载。
- 解压失败只重试解压；测试核对了服务器没有收到新的文件请求。
- 分卷没选全时不解压，报告 `missing_parts`。
- 重启不会自动恢复任何任务。
- 登录失效不影响解压本地已有文件；换账号后不能解压之前账号的文件。
- 隐藏、私人、待确认作品不能解压，也不出现在任务列表里。

## 8. 用户在本检查点追加的功能（2026-10-31）
### Steam 式底部栏与下载页
真实模式下，每页底部都有下载栏，显示当前作品、进度、速度，或“N 个项目中的 M 项已完成”。点击进入 `/downloads`：顶部是当前任务（封面、网络速度、峰值、进度、估计剩余时间、暂停），下面是“有更新”“即将进行”“已完成”。它替代了 C4 的任务弹窗；演示模式保留原弹窗。

速度由后端按实际写入字节测量，这取代了 C4 “不显示速度”的决定。**真实速度未验证。**

### 自动检查更新
**解释**：检查已下载作品有没有新版本（参照用户截图的 Steam“已启用自动更新”），不是 Atlas 软件自身的更新。

- 默认开启，每 24 小时最多一次，服务启动 60 秒后第一次检查，用的是普通同步。下载页右上角可关闭。
- **这改变了 C3 “只有用户点击才同步”的规则**，是用户要求的。不需要登录的情况下不会自动登录。
- 只提示，**不自动下载**。旧文件保留，新文件改名。
- 依据是 `upgrade_date` 字段发生变化。**字段含义未在真实作品上核实。**

### 详情页介绍图
大图、左右箭头、缩略图、“共 N 张”，支持方向键。没有图的作品不显示空框。

- 来源：公开的 `www.dlsite.com/<分区>/api/=/product.json` 的 `image_main`、`image_samples`。打开详情页时才请求，不带会话，结果保存一周，失败时保留已有内容。
- 同时用 `intro_s` 填补空的简介，不覆盖已有内容。
- 只有普通可见作品才会请求；图片走 Atlas 路由，只允许平台图片主机，按序号取，请求不能指定地址。
- **字段已用一个与用户账号无关的公开作品核实**（2026-10-31）。用户库内作品的实际显示需要人工检查。
- 图片缓存在数据目录 `cache/covers`，和封面相同，未加密，没有自动清理。

### 用户反馈与修改
| 反馈 | 修改 |
| --- | --- |
| 竖图的大图和缩略图都被裁切 | 大图脱离网格流，避免被撑高后裁切；缩略图改为完整显示。合成测试原来都是横图所以没测出，现在第一张是竖图，并断言图片不超出展示框（修复前确认失败） |
| 点箭头切换很慢 | 本机实测第一次约 170 ms、看过的图 2–16 ms，未复现“很久”，当时机器正在跑回归。已改：旧图保留到新图就绪，慢时显示“正在读取…”，打开页面就加载全部缩略图。**用户机器上的效果需要人工检查** |
| 只有箭头卡，点缩略图很快；一部作品只卡第一次 | 根因：切换时用 `scrollIntoView` 跟随缩略图，缩略图条在屏幕下方时会带动整页滚动（实测跳 467 像素）。现在只滚动缩略图条本身，并加了回归测试（修复前确认失败）。**用户机器上是否完全不卡需要人工检查** |
| 箭头按好多次才动，缩略图正常 | 根因：全站按钮按下时的 `transform: translateY(1px)` 覆盖了箭头用于居中的 `translateY(-50%)`，按下瞬间箭头下跳 21 像素，松开时鼠标已不在按钮上，点击丢失（上半部和中心都无效）。改为不用 `transform` 居中。“回到顶部”有同样问题，一并修复。两者都有真实鼠标的回归测试（修复前确认失败）。之前的脚本 `.click()` 绕过了命中判断，所以没测出来 |
| （测试发现）下载页当前任务不能取消 | 增加取消按钮 |

### 修复的问题：写入时数据库被锁
下载写进度时，其他“先读后写”的事务可能立即失败（`database_unavailable`），同步、改备注都会受影响。现在所有写事务用 `BEGIN IMMEDIATE` 排队等待，并增加了压力测试。

## 10. 已知限制
- 带密码的压缩包不支持。
- 需要序列号的作品（C4）不支持。
- ZIP 里编码既非 UTF-8 标记也非 cp932 的文件名会被拒绝，不尝试其他编码。
- 7-Zip 的进度来自输出目录的字节数；压缩包声明不准时进度也不准。
- 路径过长时报告写入失败，没有单独的错误码。
- 上限是经验值，没有真实作品数据支撑。
- 解压结果没有自动清理，“重新解压”会产生新文件夹。
- 更新检查用整库同步，一次约 6 个批量请求，不是按作品单独查询。
- 下载页同时列出同一作品的下载和解压记录。
