# Phase 2 · 检查点 8 报告：跨盘发现与批量本地导入

日期：2026-10-31 · 分支 `phase-2/checkpoint-8`。

## 1. 结论
**实现完成，真实库只读核对通过，批量关联待用户确认。** 夜间没有在真实资料库建立任何关联。

## 2. 真实结构（只读核对，用户指定的库）
`<库>/<类型>/<制作方>/<作品名>/`，类型是 Game、Audio、Comic、Illust、Movie。文件夹名里**没有作品编号**。比对结果：第一层 161 个中 155 个是制作方，第二层 288 个中 254 个是作品名。

没有解析 DLsite Nest 的数据文件，只看文件夹名。

## 3. 发现
- 快速模式：检查所选盘的常见位置和已保存的库。深入模式：按目录向下（6 层，40 万个文件夹上限），跳过系统目录和回收站，不跟随符号链接和联接点。到达上限时明确说“范围没查完”。
- 识别规则：要有 `类型/制作方/作品名` 的深度，并且名字像库，或者有两种以上类型。只有一个叫 Game 的文件夹不算。
- 网络盘列出但不访问。指定文件夹由用户决定。
- 只读文件夹名：不打开文件、不计算哈希、不运行程序。

## 4. 匹配
| 结果 | 依据 | 处理 |
| --- | --- | --- |
| 可确定 | 文件夹名里有作品编号，且在作品库中 | 可导入 |
| 很可能 | 制作方和作品名都相同（忽略全半角、大小写、标点） | 用户接受后导入 |
| 需要确认 | 只有作品名相同，或多部同名 | 逐条选择，绝不替用户挑 |
| 没有匹配 | 作品库里没有 | 保留在列表里，不创建作品，不声称拥有 |

隐藏、私人、待确认的作品不参与匹配，不会被文件夹暴露。

**与 prompt 的差异**：prompt 要求夜间只自动提交稳定 ID 精确匹配。用户的库文件夹名没有 ID，所以夜间什么也没自动提交。

## 5. 导入
- 用户点一下批量关联“可确定”和“很可能”。复用 C7 的本地副本，来源标记 `scanned`。唯一候选程序才作为主程序。
- 同一作品在多个盘是多个副本。重复扫描不重复，已关联和已忽略的决定保留。
- 撤销只删这一批新增的关联，不动文件。

## 8. 用户决定后的变更（2026-10-31）
用户要求扫盘后自动关联，不要手动操作。

- 启动时、每次同步后、点“重新扫描并关联”时，查找各固定盘的 `DLsiteNest\Library`，明确的匹配直接关联。移动盘和网络盘不自动扫。
- 常见位置只保留这一个（用户确认库一定在这里）。其他位置用高级选项指定。
- 放宽匹配：作品名完全相同且库里只有一部（至少 6 个字符），即使制作方写法不同，也算匹配。制作方相同且作品名只差副标题（至少 8 个字符、多出的部分没有数字），也算匹配。
- 文件夹名末尾的版本号（`ver121`、`v1.2.3`、`(Ver.1.21)`）不算作品名。光秃秃的数字可能是另一卷，不去掉。
- 制作方相同且作品名相似度 85% 以上、数字相同、只有这一部，也算匹配。相似度 60% 以上进“需要确认”，最多列 3 个候选。
- 多部同名、很短的作品名仍然留给用户，绝不替用户选。
- 撤销后这些文件夹标记为已拒绝，以后扫描不再自动关联；点“关联 N 部匹配的作品”才会重新关联。
- 详情页的手动入口改名“手动指定文件夹”，保留用于没匹配上的作品。
- 第 4 节“用户接受后导入”和第 5 节“用户点一下批量关联”由此变更取代。

有风险的地方：作品名相同但其实不是同一部时会关联错，可以撤销。

## 9. 已知限制
- 没有匹配的文件夹不会变成本地作品条目（需求草案中的“本地条目”首批未做）。
- 作品名是同步时选的语言。文件夹是另一种语言时匹配不上，会进“没有匹配”。
- 增量检查就是再扫一次已保存的库。
- 没有卷序列号，盘符改变要靠重新扫描或手动重新定位。
